## 제목 후보

- React는 왜 내 패널을 다시 만들었나 — key, 부모, 그리고 순서
- 미리보기만 했을 뿐인데 입력값이 사라졌다
- 레이아웃과 DOM을 분리해 iframe 재로드를 없애기
- "위치"와 "내용"을 나누면 생기는 일: 패널 레이아웃 라이브러리의 렌더 구조 개편

## 한 줄 요약

패널을 드래그하면 **드래그하지 않은 패널**까지 리마운트되거나 DOM에서 떼였다 붙어 입력값·스크롤이 초기화되고 iframe이 다시 로드됐다. 원인은 "중첩 DOM이 곧 레이아웃"인 구조였다. 그래서 레이아웃은 빈 slot으로 이루어진 골격이 계산하고, 패널은 루트 바로 아래에 고정된 순서로 둔 채 좌표만 받도록 렌더를 나눴다. 공개 API는 바꾸지 않았다.

## 자기소개서·포트폴리오용 요약

### 한 문장

> React 패널 레이아웃 라이브러리에서 드래그 미리보기가 다른 패널의 상태를 초기화하고 iframe을 다시 로드하던 문제를, 레이아웃 계산(골격)과 패널 DOM을 분리하는 렌더 구조로 해결했다. 공개 API는 유지했고, 실제 브라우저 입력으로 도는 회귀 테스트 4케이스를 실패에서 통과로 바꿨다.

### STAR

| | 내용 |
|---|---|
| **상황** | 직접 만든 마이크로 프론트엔드 QA 랩에서 실제 마우스 입력으로 라이브러리를 검수하던 중, 패널을 끌어 **놓지도 않고 미리보기만 해도** 옆 패널의 입력값·카운터·스크롤이 사라지고 iframe 패널(다른 팀의 remote)이 다시 로드되는 것을 발견했다(sev-2, 재현 2/2). |
| **과제** | 드래그의 어느 시점(hover, 취소, 커밋)에도 드래그하지 않은 패널은 언마운트·DOM 재삽입·재로드되지 않아야 했다. 제약은 세 가지였다. 공개 API·트리 형식을 바꾸지 않는다, 외부 라이브러리를 추가하지 않는다, split 노드에 ID를 넣지 않는다(경로로 식별하는 설계 원칙). |
| **행동** | ① React 재조정 규칙으로 원인을 셋으로 나눴다(형제 인덱스 key, 부모 변경, 같은 부모 안 순서 변경). ② key 안정화·오버레이 미리보기·portal·평평한 렌더 등 선택지를 "어떤 원인까지 없애는가"로 비교했다. ③ 골격(빈 slot)과 패널 레이어(루트 바로 아래, 고정 순서, `position: absolute`)로 렌더를 나누고, `useLayoutEffect`와 `ResizeObserver`로 slot 좌표를 페인트 전에 패널에 반영했다. ④ 테스트 도구가 바뀐 DOM을 읽도록 고치면서, 그 변경이 **옛 코드의 결과를 바꾸지 않는다는 것**을 먼저 증명했다. |
| **결과** | 회귀 스펙 4케이스가 수정 전 2/2 실패에서 수정 후 2/2 통과로 바뀌었다. 스모크 19, 회귀 14(마우스)·15(터치), 스파이크 59로 기존 테스트가 하나도 깨지지 않았다. 플레이그라운드 검사 61/61(StrictMode, 중첩 레이아웃, `transform: scale` 컨테이너 포함)도 통과했다. 소스 6파일(+212/−77)을 바꿨고, 공개 API를 바꾸지 않은 패치 버전 1.0.1로 배포했다. |

### 보여 줄 수 있는 역량

- **원인을 메커니즘 단위로 쪼개기**: "리마운트된다"는 증상 하나를 React가 인스턴스를 식별하는 세 규칙으로 나눴고, 각 규칙이 어느 테스트 케이스에 대응하는지 맞췄다.
- **선택지를 기준을 세워 비교하기**: 가장 작은 수정(key 안정화)이 어디까지만 고치는지 먼저 확인하고, 부분 수정으로는 이슈가 닫히지 않는다는 것을 근거로 큰 변경을 택했다.
- **트레이드오프를 숨기지 않기**: DOM 순서 ≠ 화면 순서(Tab·스크린리더 순서), SSR 첫 화면을 문서와 CHANGELOG에 적었다.
- **검증 도구 자체를 검증하기**: 테스트 헬퍼를 고칠 때 "고친 헬퍼 + 옛 코드 = 이전과 같은 결과"를 먼저 보였다. 테스트를 고쳐서 통과시키지 않았다는 증거다.

### 면접에서 나올 만한 질문

| 질문 | 답의 요지 |
|---|---|
| split key만 안정화하면 되지 않나? | 형제 인덱스가 밀리는 경우(#19 a)만 고쳐진다. 부모 split이 바뀌는 경우(루트 감싸기, split 풀림)는 key가 같아도 React가 리마운트하고, 같은 부모 안 순서 변경은 리마운트 없이도 DOM을 옮겨 iframe을 다시 로드한다(#20). 회귀 스펙을 두 케이스로 나눠 둔 것도 부분 수정을 걸러 내기 위해서다. |
| React portal로 내용만 보존하면? | React 상태는 남지만 portal의 host 요소를 옮기는 것도 DOM 재삽입이라 iframe 재로드와 스크롤 초기화는 남는다. |
| `Element.moveBefore()`(상태 보존 이동)는? | React가 아직 쓰지 않고 브라우저 지원도 제한적이다. 쓰더라도 "DOM을 옮긴다"는 구조 자체는 그대로다. |
| 좌표를 트리에서 직접 계산하지 않은 이유는? | flex 비율, min/max 제약, Resizer 두께를 다시 구현해야 한다. 빈 slot으로 된 골격을 그대로 flex로 배치시키면 브라우저가 계산하고, 기존 CSS 제약 의미도 그대로 유지된다. |
| 위치를 늦게 반영해 깜빡이지 않나? | 위치는 `useLayoutEffect`(커밋 직후, 페인트 전)에서 쓴다. 자식의 layout effect(slot·패널 등록)가 부모보다 먼저 실행되므로 같은 커밋 안에서 맞춰진다. 창 크기 변화는 `ResizeObserver`가 레이아웃 뒤·페인트 전에 처리한다. |
| 접근성 영향은? | 패널 DOM 순서가 화면 순서와 달라져 Tab·스크린리더 순서가 "처음 나타난 순서"를 따른다. DOM을 옮기지 않는 것과 맞바꾼 것이라 CHANGELOG에 명시했다. |

## 1. 문제: 미리보기만 했는데 옆 패널이 초기화된다

### 어떻게 찾았나

1.0.0을 준비하면서 만든 QA 랩(Harbor Workbench, [road-to-1.0.0.md](./road-to-1.0.0.md) 3절)이 run 01에서 찾았다. 랩은 Module Federation remote, 별도 React 루트로 마운트되는 remote, iframe remote를 한 레이아웃에 띄우고, Playwright로 **실제 마우스 입력**(CDP 드래그 인터셉트)을 보낸다. 패널마다 마운트 카운터, iframe 로드 카운터, DOM 이동 로그(MutationObserver)가 붙어 있다.

### 관측 (run 01, R01 — 트리 `H[p-a, V[p-b, p-c], p-d]`, `p-d`를 `p-a` 왼쪽에 hover → Esc)

| 시점 | 패널 | 마운트 변화 | DOM 이동 | 내용 상태 |
|---|---|---|---|---|
| hover | `p-b`, `p-c` | +1 / +1 (리마운트) | — | 입력값·카운터·`scrollTop` 초기화 |
| hover | `p-a` | +0 | +1 (떼었다 붙음) | 입력값 유지, `scrollTop` 120 → 0 |
| Esc 뒤 누적 | `p-b`, `p-c` | +2 / +2 | — | 초기화 |

- iframe 패널이면 hover만으로 문서 `loads` +1(문서 요청 +1, 프레임 안 입력 소실). 별도 React 루트 remote는 루트를 새로 만들었다.
- 커밋(드롭), `movePanel`·`insertPanel`·`removePanel` 같은 API 호출에서도 같은 메커니즘이 반복됐다(R16·R17).
- 심각도 sev-2. 화면이 멈추지는 않지만, 드래그를 **취소해도** 다른 팀 remote의 상태가 사라진다.

## 2. 원인: React가 "같은 패널"을 판단하는 방식

### 렌더 vs DOM 이동 vs 리마운트

| 종류 | React가 하는 일 | 입력값·state | 스크롤·iframe |
|---|---|---|---|
| 리렌더 | 컴포넌트를 다시 실행하고 바뀐 속성만 DOM에 반영. 노드는 그대로 | 유지 | 유지 |
| DOM 이동 | 같은 노드를 부모에서 떼었다 다른 위치에 붙임 | 유지 | **초기화, iframe 재로드** |
| 리마운트 | 컴포넌트와 노드를 버리고 새로 만듦 | **사라짐** | 초기화 |

React는 **같은 부모 아래, 같은 key**이면 같은 인스턴스로 본다. 부모나 key가 다르면 리마운트하고, 순서가 바뀌면 DOM을 옮긴다.

### 옛 구조: 중첩 DOM이 곧 레이아웃

```
div[data-tree-root]
└── split H                         (flex row)
    ├── panel p-a  + 내용           (key: p-a)
    ├── split V                     (key: split-1)   ← 형제 인덱스 key
    │   ├── panel p-b  + 내용       (key: p-b)
    │   └── panel p-c  + 내용       (key: p-c)
    └── panel p-d  + 내용           (key: p-d)
```

드래그 중에는 `TreeLayout`이 실제 트리 대신 미리보기 트리를 **같은 자리에** 렌더했다. 그러면 세 가지 일이 생긴다.

| 원인 | 예 | 결과 | 이슈 |
|---|---|---|---|
| split key가 형제 인덱스 | `[p-a, split-1, p-d]` → `[p-d, p-a, split-2]` | `split-1`이 사라지고 `split-2`가 생김 → `p-b`·`p-c` 리마운트 | #19 (a) |
| 부모 split이 바뀜 | 루트 가장자리에 놓아 루트가 새 split으로 감싸짐, 자식이 하나 남은 split이 풀림 | key가 같아도 부모가 달라 리마운트 | #19 (b) |
| 같은 부모 안 순서 변경 | 위와 같은 재배열에서 `p-a`가 뒤로 밀림 | React가 `insertBefore`로 `p-a`를 옮김 → `scrollTop` 0, iframe 재로드 | #20 |

세 번째가 핵심이었다. DOM을 옮기는 순간 iframe은 다시 로드되므로, **DOM 중첩이 레이아웃인 한** 어떤 key 전략으로도 #20은 닫히지 않는다.

| #19 (b) 부모 변경 | ❌ | ✅(hover·취소만) | ✅ | ✅ |
| #20 순서 변경 → 재삽입 | ❌ | hover·취소만 | ❌(host 이동도 재삽입) | ✅ |
| 커밋·API 호출 | 일부 | ❌ | 리마운트만 해결 | ✅ |

- CSS `order`로 화면 순서만 바꾸는 방법도 검토했지만, 같은 부모 안의 재배열에만 통하고 부모 변경은 해결하지 못한다.

## 4. 설계: 골격과 패널 레이어

### 구조

```
div[data-tree-root]  (position: relative)
│
├── [골격] 기존과 같은 중첩 flex. 패널 자리에는 빈 slot만 있다
│   └── split H
│       ├── slot p-a        (빈 div. flex 비율, min/max 담당)
│       ├── Resizer
│       ├── split V
│       │   ├── slot p-b
│       │   ├── Resizer
│       │   └── slot p-c
│       ├── Resizer
│       └── slot p-d
│
└── [패널 레이어] 루트 바로 아래에 평평하게, 순서 고정, position: absolute
    ├── panel p-a + 내용    ◄── slot p-a의 위치·크기를 복사
    ├── panel p-b + 내용    ◄── slot p-b
    ├── panel p-c + 내용    ◄── slot p-c
    └── panel p-d + 내용    ◄── slot p-d
```

- **골격**은 "어디에"를 계산한다. 트리가 바뀔 때마다 마음대로 다시 그려도 된다. 비어 있어서 리마운트돼도 잃을 것이 없다. flex 비율, min/max, Resizer는 원래 코드 그대로다.
- **패널 레이어**는 "무엇을"을 들고 있다. 트리 모양이 아무리 바뀌어도 패널은 항상 루트라는 같은 부모 아래에 같은 순서로 있다. 그래서 React가 패널을 파괴하거나 옮길 이유가 없다.
- 트리 데이터·공개 API·트리 JSON은 그대로다. 사용자는 여전히 트리 하나만 다룬다.

### 같은 순서인데 어떻게 화면 배치가 바뀌나

`position: absolute` 요소는 `left/top/width/height`로 놓이고, DOM에서 몇 번째인지는 화면 위치와 무관하다. 루트 1200×600, 비율이 모두 1일 때:

```
hover 전: H[p-a, V[p-b, p-c], p-d]       hover 중: H[p-d, p-a, V[p-b, p-c]]
p-a: x=0    w=400                        p-d: x=0    w=400
p-b: x=400  y=0   h=300                  p-a: x=400  w=400
p-c: x=400  y=300 h=300                  p-b: x=800  y=0   h=300
p-d: x=800  w=400                        p-c: x=800  y=300 h=300
패널 DOM 순서: [p-a, p-b, p-c, p-d]       패널 DOM 순서: [p-a, p-b, p-c, p-d]  ← 그대로
```

### 구현 포인트

| 파일 | 역할 |
|---|---|
| `src/hooks/usePanelPlacement.ts` (신규, 77줄) | slot·패널 등록, 위치 동기화 |
| `src/components/PanelSlot.tsx` (신규, 32줄) | 골격 안의 빈 자리. `flex`·min/max를 여기로 옮김 |
| `src/components/LayoutNodeRenderer.tsx` | 골격 전용. 패널 대신 `PanelSlot`을 렌더 |
| `src/components/TreeLayout.tsx` | 루트 `position: relative`, 골격 + 고정 순서 패널 목록 |
| `src/components/PanelNodeRenderer.tsx` | `position: absolute`, 드롭 위치는 자기 slot 기준 |
| `src/hooks/useTouchDrag.ts` | 터치 드롭 위치도 앵커의 slot 기준 |

1. **위치 동기화 시점.** `useLayoutEffect`(deps 없음)로 매 렌더의 커밋 직후·페인트 전에 slot rect를 패널 style에 쓴다. 자식(slot·패널)의 등록 layout effect가 부모(TreeLayout)보다 먼저 실행되므로 같은 커밋 안에서 맞는다. 창·컨테이너 크기처럼 렌더 없이 바뀌는 경우는 `ResizeObserver`(루트와 모든 slot 관찰)가 잡는다.

   ```ts
   panelsRef.current.forEach((panel, id) => {
     const slot = slotsRef.current.get(id);
     if (!slot) return;
     const rect = slot.getBoundingClientRect();
     panel.style.left = `${(rect.left - rootRect.left) / scaleX - root.clientLeft}px`;
     // top / width / height도 같은 방식
   });
   ```

2. **React와 충돌하지 않게.** `left/top/width/height`는 훅이 직접 쓰고, React style 객체에는 넣지 않는다. React는 style 객체에 있는 키만 비교·갱신하므로 덮어쓰지 않는다.
3. **`transform: scale` 보정.** `getBoundingClientRect`는 화면 px라서 조상이 확대·축소돼 있으면 어긋난다. `rootRect.width / root.offsetWidth`로 배율을 구해 루트 기준 CSS px로 되돌린다. 열리는 애니메이션 중인 모달처럼 RO가 다시 불리지 않는 경우도 처음부터 맞게 하기 위해서다.
4. **고정 순서.** "남은 패널은 기존 순서 유지 + 새 패널은 뒤에 추가"로 순서를 만든다. 멱등이라 StrictMode의 이중 렌더에도 안전하다.
5. **드롭 위치 계산.** `getDropTarget`은 DOM 조상을 따라 올라가며 split을 찾는다(루트·split 가장자리 판정). 패널이 더는 split 안에 있지 않으므로, 패널 대신 **같은 id의 slot**을 넘긴다. slot의 rect는 패널과 같다. 함수 자체는 바꾸지 않았다.
6. **중첩 TreeLayout.** 안쪽 레이아웃이 바깥 패널의 크기가 정해지기 전에 한 번 배치되지만, 바깥 배치로 안쪽 루트 크기가 바뀌면 안쪽 RO가 같은 프레임(레이아웃 뒤·페인트 전)에 다시 배치한다. 플레이그라운드에서 정렬 오차 0.5px 이내를 확인했다.

### 테스트 도구도 바꿔야 했다

랩의 헬퍼 두 개가 옛 DOM 구조를 전제로 했다.

- `readDomTree`: DOM을 따라 내려가며 `H[p-a,V[p-b,p-c],p-d]` 같은 표기를 만든다. 패널이 split 안에 중첩돼 있다고 가정했다.
- `dropPoint`: "p-a 왼쪽, depth 1" 같은 드롭 지점 좌표를 계산하려고 패널의 DOM 조상에서 split을 찾았다.

둘 다 "slot이 있으면 slot을 읽고, 없으면 예전처럼 패널을 읽게" 고쳤다. 그리고 **고친 헬퍼로 옛 코드를 돌려 결과가 바뀌지 않는 것을 먼저 확인**했다. 테스트를 고쳐서 수정을 통과시킨 것이 아니라는 증거다.

### 수정 때문에 "정당하게" 바뀐 기대값

- **스파이크 S3**은 "미리보기가 소스 패널을 리마운트한다"를 전제로, 분리된 원본에 `dragend`가 도착하는지 확인하는 하네스 게이트였다. 이번 수정으로 그 전제가 더는 성립하지 않아 실패했다. 전제만 빼고 돌리면 나머지(drop 없음, `onMovePanel` 0, 트리 불변, 불변식 I1~I7)는 통과했다. 그래서 같은 제스처에서 "소스가 리마운트되지 않고 `dragend`가 연결된 소스로 온다"를 확인하도록 바꿨다. 분리된 노드 경로는 npm 0.5.1 빌드를 쓰는 S5가 계속 확인한다.
- **이벤트 로그 기준선**도 바뀌었다. 소스가 분리되지 않으니 `dragend`가 capture/target/bubble로 정상 전파되고(S3·S4), 리마운트되던 형제 패널의 `dragleave`가 이제 빠지지 않는다(S2). 버그 수정의 부수 효과로 **이벤트 시퀀스가 정상화**된 것이다.

### 플레이그라운드 61/61

랩이 다루지 않는 환경을 따로 확인했다(StrictMode, 중첩 TreeLayout, iframe 패널, `transform: scale(0.5)` 컨테이너, Playwright 실제 마우스 드래그).

- hover·Esc·드롭·루트 감싸기·API `movePanel`/`insertPanel`/`removePanel` 각각에서 리마운트 0, 패널 DOM 제거 0, iframe 재로드 0, 입력값·`scrollTop` 유지
- 모든 패널 rect = slot rect(±0.5px), 경계선 리사이즈 시 `maxWidth` 준수, 창 리사이즈 시 `minWidth` 준수
- 콘솔 에러·경고 없음

한 번은 드롭이 커밋되지 않아 실패했다. 하지만 **옛 코드에서도 똑같이 재현**돼 테스트 절차 문제로 판단했다(랩처럼 소스 패널 헤더 위에서 놓아야 커밋된다). 결론을 내리기 전에 옛 코드와 비교하는 습관이 헛수고를 막았다.

## 6. 감수한 것

- **DOM 순서 ≠ 화면 순서**: 패널 DOM 순서는 처음 나타난 순서다. Tab 포커스·스크린리더 순서가 화면 순서와 다를 수 있다. DOM을 옮기지 않는 것과 맞바꾼 것이다.
- **SSR**: 패널 위치는 클라이언트에서 정해지므로 서버 HTML에는 위치가 없다.
- **사용자 CSS**: `[data-panel-id]`가 split 안의 flex 아이템이라고 가정한 CSS는 slot(`[data-panel-slot]`) 기준으로 바꿔야 한다. 문서화된 구조는 아니었다.
- **비용**: 렌더마다 slot rect를 패널 수만큼 읽는다(페인트 전 1회).

## 8. 배운 것

1. **"다시 렌더"와 "다시 만듦"은 다르다.** React에서 문제는 렌더 횟수가 아니라 인스턴스 식별(부모 + key)과 DOM 이동이다. 리렌더는 무해하지만 DOM 이동은 iframe과 스크롤을 초기화한다.
2. **위치와 내용을 분리하라.** 레이아웃이 바뀔 때마다 내용까지 따라 움직이는 구조는 상태를 잃는다. 위치 계산은 빈 골격에 맡기고, 내용은 한곳에 두고 좌표만 바꾸면 된다.
3. **브라우저가 잘하는 계산은 브라우저에 맡겨라.** 좌표를 직접 계산하는 대신 빈 slot을 flex로 배치시켜 측정했다. min/max 같은 기존 CSS 의미를 다시 구현하지 않아도 됐다.
4. **가장 작은 수정이 어디까지 고치는지 먼저 확인하라.** key 안정화만으로는 케이스 (a)만 닫힌다. 회귀 스펙을 원인별 케이스로 나눠 두면 부분 수정을 바로 알 수 있다.
5. **테스트 도구를 바꿀 때는 옛 코드로 중립성을 증명하라.** 그래야 "테스트를 고쳐 통과시켰다"는 의심을 받지 않는다.
6. **게이트 테스트의 실패는 전제와 회귀를 구분해서 읽어라.** S3은 수정이 의도대로 동작해서 실패했다. 전제만 빼고 다시 돌려 나머지가 통과하는 것을 확인한 뒤에 기대값을 바꿨다.
